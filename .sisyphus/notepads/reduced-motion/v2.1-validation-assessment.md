# Momus v2.1 Real-World Validation Assessment

**Date:** 2026-05-06  
**Project:** Rotating-X (React 19 / Vite 7)  
**Feature validated:** `prefers-reduced-motion` accessibility support  
**Skills under test:** `momus-prd-reviewer` and `momus-plan-reviewer`

---

## 1. Feature Selection

**Selected:** `prefers-reduced-motion` — disable `hudPulse` and slow rAF speed for accessibility.

**Why this feature:**
- Listed as the #1 "Near Term" item in the project's own README roadmap
- Small enough to scope in a single PRD but real enough to exercise all review categories
- Touches React hooks, `requestAnimationFrame`, styled-components, and CSS media queries — giving the reviewers multiple integration surfaces to scrutinize
- The codebase has NO test infrastructure, which creates natural tension between "testable acceptance criteria" and reality — a good stress test for the review skills

---

## 2. PRD Review Results (`momus-prd-reviewer`)

**Gate Decision:** `WARNING`

**Blockers found:** 4 total (0 critical, 3 major, 1 minor)

| ID | Severity | Category | Title | Verdict |
|---|---|---|---|---|
| A-1 | MAJOR | Logical Contradiction | Conflicting `FancyButton` integration model | **Legitimate** — PRD simultaneously said FancyButton consumes hook directly, may use prop/context/hook, and has already decided to use a prop. These are mutually exclusive. |
| B-1 | MAJOR | Scope Creep | Hook unit test assumes infrastructure that is not in scope | **Legitimate** — PRD requires a unit test but the repo has no test runner. The "Out of Scope" section even explicitly says test runner setup is out of scope. |
| B-2 | MINOR | Scope Creep | CSS containment broadens scope beyond the reduced-motion objective | **Legitimate** — `contain: layout paint` is a separate paint-optimization concern. Bundling it adds unrelated acceptance surface and introduces a known clipping risk. |
| C-1 | MAJOR | Missing Verification | Acceptance is not mechanically verifiable in this repository | **Legitimate** — The PRD relies on external OS/device settings and manual visual checks. No repo-executable verification path exists. |

**False positives:** None. Every blocker points to a real issue that would have caused confusion or rework during implementation.

**Assessment of strictness:** **Appropriately rigorous.** The PRD was not FAILed because the core scope (reduced-motion hook + component integration + CSS overrides) is sound. The WARNING correctly signals "proceed with fixes" rather than "start over." The skill caught subtle contradictions (A-1) that a human skim might miss, and the scope-creep call (B-1) is exactly the kind of thing that causes teams to miss sprint deadlines.

## 3. Plan Review Results (`momus-plan-reviewer`)

**Gate Decision:** `FAIL`

**Blockers found:** 4 total (0 critical, 4 major, 0 minor)

| ID | Severity | Category | Title | Verdict |
|---|---|---|---|---|
| D-1 | MAJOR | Dependency Gap | `FancyButton` slice is not independently verifiable | **Legitimate** — Slice 1.3 claims it only depends on Slice 1.1, but no live `FancyButton` in the app receives props until Slices 3.1 and 3.2 land. The verification step "hover a FancyButton with Reduce Motion ON" is impossible at the claimed stage. |
| E-1 | MAJOR | Integration Risk | Cube plan does not satisfy live preference changes | **Legitimate** — The plan only changes initial `rotationSpeed` and guards future mouse events. If reduced motion is toggled ON mid-session after the cube has already accelerated, the rAF loop keeps the high speed. The PRD explicitly promises live mid-session updates (Story 3.1). |
| E-2 | MAJOR | Integration Risk | Reduced-motion buttons still retain hover movement | **Legitimate** — The plan disables only the `hudPulse` animation, but `FancyButton` hover also includes `transform: translateY(-2px)` with a `0.3s` transition. This is still motion during interaction, which contradicts the accessibility goal. |
| F-1 | MAJOR | Resource Risk | Browser support assumption for live media-query listeners is too broad | **Legitimate** — The plan assumes `matchMedia` + `change` events work uniformly across the entire stated browser matrix. Older Safari versions used a different listener API (`addListener` / `removeListener`). This would cause silent failures on live toggles for some users. |

**False positives:** None. Every blocker represents a real execution risk.

**Assessment of strictness:** **Appropriately rigorous.** A FAIL is correct here — following the plan literally would result in:
1. A cube that ignores live accessibility toggles (E-1)
2. Buttons that still move on hover in "reduced motion" mode (E-2)
3. A slice that claims to be verifiable when it cannot be tested in-app (D-1)
4. A browser compatibility gap that would silently break the feature for some users (F-1)

These are not nitpicks. They are execution blockers that would ship a broken accessibility feature.

## 4. Overall Assessment

### Did the skills provide value?

**Yes — significant value.**

- **PRD reviewer** prevented three sources of downstream confusion (ownership ambiguity, phantom test dependency, scope bundling) and flagged that the acceptance criteria could not be objectively verified. These are exactly the issues that cause sprint retrospectives to say "we should have caught that in planning."
- **Plan reviewer** caught four execution blockers that the PRD reviewer could not catch because they only exist at the plan level (slice dependencies, runtime integration paths, browser API compatibility). The mid-session toggle gap (E-1) and the residual button motion (E-2) are particularly good catches — they show the skill understood the actual component code, not just the plan text.

### Are the skills too strict, too lenient, or appropriately rigorous?

**Appropriately rigorous.**

- The PRD got `WARNING` (not `FAIL`) because the core scope is sound. The skill correctly distinguished between "needs polish" and "fundamentally broken."
- The plan got `FAIL` because following it literally would ship broken behavior. The skill correctly distinguished between "looks good on paper" and "will actually work in the browser."
- No invented blockers. Every issue is traceable to a specific PRD/plan line and a specific code behavior.

### Gaps identified

1. **No false-positive stress test in this session.** Both the synthetic test (previous session) and this real-world test produced zero false positives. A truly rigorous validation would also test a "known-good" PRD/plan to confirm the skills do not over-flag. This is recommended before declaring production-ready.

2. **Plan reviewer did not reference the PRD reviewer's findings.** The plan reviewer correctly fixed two PRD problems (FancyButton ownership ambiguity, unit-test infrastructure gap), but it did not explicitly cite the PRD review as its source. In a real chain workflow, the plan reviewer should read the PRD review report and confirm each prior finding was addressed. This is a workflow integration gap, not a skill logic gap.

3. **No severity calibration guidance.** Both reviewers use CRITICAL / MAJOR / MINOR but do not explain when a category deserves CRITICAL vs MAJOR. In this session, no CRITICAL blockers were found. It is unclear whether the skills are calibrated to rarely use CRITICAL (good) or whether they under-weight issues that could block a release (bad). More sessions needed.

4. **The plan reviewer caught issues in the PRD that the PRD reviewer missed.** E-2 (residual button hover movement) and E-1 (live toggle gap) are arguably PRD-level issues, not plan-level issues. The PRD reviewer did not catch them because it reviewed requirements in isolation, while the plan reviewer had to map requirements to actual code paths. This suggests the PRD reviewer could benefit from a "trace requirements to existing code" step, but it also validates the two-gate architecture: Gate 2 (plan review) caught things Gate 1 (PRD review) missed.

### Is the v2.1 architecture ready for production?

**Yes, with one recommended addition.**

The split into `momus-prd-reviewer` and `momus-plan-reviewer` is working as designed:
- Gate 1 catches requirements-level problems before slicing begins
- Gate 2 catches execution-level problems before implementation begins
- The two skills complement each other (plan reviewer found things PRD reviewer missed)

**Recommended addition:** Run a "known-good" validation — create a deliberately clean PRD and plan for a trivial feature, then confirm both reviewers return `PASS` with zero or near-zero blockers. This calibrates against over-flagging. If they return `WARNING` or `FAIL` on a genuinely clean artifact, the severity thresholds need adjustment.
